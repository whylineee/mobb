# AgentWatch: план системи моніторингу агентів

Статус: планування. Код не пишемо, дослідження ще не запускали.

## 1. Мета

Локальний веб-дашборд на macOS, який у **live-режимі** показує агентів, що працюють на моєму комп'ютері: хто запущений, над якою задачею працює, що робить просто зараз, у якому стані.

Агенти на старті: **Claude Code** і **Codex**.

## 2. Ухвалені рішення

- Платформа: macOS.
- Інтерфейс: локальний вебзастосунок з інтерактивним ізометричним 3D-офісом (Virtual Office), маленькими роботами-агентами та детальною панеллю вибраної сесії.
- Головне на екрані: live-статус і поточна задача кожного агента.
- Збір даних: комбінація hooks і сканування процесів та логів.
- Стек: повністю TypeScript.
- Тільки перегляд (без дій над агентами), історія в SQLite, нотифікації на другому етапі.

## 3. Вимога live

- Нова сесія з'являється на дашборді одразу після старту (ціль: до 1 секунди).
- Зміна стану або поточного інструмента видна без перезавантаження сторінки.
- Завершена або вбита сесія зникає або позначається як завершена без ручних дій.
- Браузер отримує дані через SSE: повний знімок при підключенні, далі лише дельти.

## 4. Архітектура

Три шари.

**Колектори** (швидкість від найшвидшого):
1. Hooks агентів: миттєві події (промпт, виклик інструмента, завершення, очікування дозволу).
2. Спостереження за файлами сесій: нова сесія та дописаний хвіст, читання з запам'ятованої позиції.
3. Сканування процесів кожні 1-2 с: чи агент живий, cwd, CPU, RAM.

**Демон:** нормалізує все в моделі `Agent` (id, тип, проєкт, cwd, статус `working | waiting | idle | ended`, поточна задача, поточний інструмент, pid, CPU/RAM, час останньої активності) та `Event` (час, агент, тип, текст). Тримає стан у пам'яті, історію пише в SQLite.

**Веб:** React-застосунок з ізометричною 3D-сценою та інформаційними панелями; стан оновлюється з SSE-потоку. 3D-візуалізація не є джерелом істини: вона лише відображає нормалізований стан демона.

## 5. Стек

Повністю TypeScript, без Python, Bash чи інших мов у коді проєкту.

- Монорепо на pnpm: `shared` (типи, zod-схеми подій), `daemon`, `web`, `hook-cli`.
- Демон: Node, Hono (HTTP + SSE + ендпоінт для hooks), chokidar (файли), бібліотека для процесів, `better-sqlite3`.
- Hook-скрипт для агентів: невелика TypeScript CLI (`hook-cli`), яка читає подію зі stdin, перевіряє її схемою з `shared` і шле демону. Командою в налаштуваннях hooks викликається саме вона, а не curl чи shell-скрипт.
- Встановлення та видалення hooks, запуск, конфіги: теж TypeScript-команди в тому ж монорепо.
- Веб: Next.js (App Router), React, Tailwind, Zustand, Three.js, React Three Fiber, Drei. Next.js використовуємо лише як оболонку інтерфейсу, вся live-логіка залишається в окремому демоні. 3D-рушій відповідає тільки за відображення сцени та взаємодії.
- Єдині типи подій і станів у `shared` для демона, hook-cli та вебу.
- Усе слухає тільки `127.0.0.1`.
- Відкрите питання для дослідження: як зробити hook-cli достатньо швидкою (холодний старт Node на кожен виклик інструмента), у плані це пункт 8.1.

## 6. Інтерфейс: AgentWatch Virtual Office (затверджена концепція)

### 6.1 Основна ідея та візуальний стиль

- Головний екран — **живий ізометричний 3D-офіс**, а не сітка звичайних карток. Кожна реальна сесія Claude Code або Codex має **окремого маленького 3D-робота та робоче місце**.
- Стиль: стилізована low-poly / cozy developer-office діорама; чиста геометрія, тепле локальне світло, темний нейтральний фон, виразні кольорові акценти. Камера ортографічна, ізометрична, приблизно 35–45° зверху; точні параметри підбираються під сцену.
- В офісі: столи, монітори, крісла, лампи, рослини, декоративні елементи та зона відпочинку. Декор не повинен закривати роботів або погіршувати FPS.
- Різні типи агентів мають візуально відмінні варіанти роботів (форма/колір/емблема), а різні сесії — унікальні підписи або короткі ідентифікатори. Не покладатися тільки на колір.
- 3D-офіс — основна навігація, а не окрема декоративна заставка. Інформація про стан завжди має залишатися читабельною.

### 6.2 Компонування екрана

- Центральна частина (орієнтовно 75–85% доступного простору) — 3D-сцена з офісом.
- Верхня компактна панель: назва AgentWatch, індикатор з'єднання з демоном, лічильники `working / waiting / idle`, загальна кількість сесій, фільтри за типом агента й проєктом.
- Невелика панель керування сценою: наближення, віддалення, скидання камери, перемикач підписів/ефектів, за потреби режим зниженої анімації.
- Короткі бейджі біля робочих місць: ім'я агента, проєкт, статус, скорочена поточна задача. Довгі тексти не розміщувати безпосередньо в 3D.
- Коли агента не вибрано — офіс максимально відкритий. Після вибору — **права детальна панель** (drawer) поверх або поруч зі сценою; камера адаптує композицію, щоб вибраний робот залишався видимим.
- На вузьких екранах панель стає повноекранною/нижньою, а 3D-сцена може спрощуватися. Основний пріоритет — desktop на macOS.
- Додаткові перегляди: компактний список сесій для пошуку/доступності; історія — після MVP.

### 6.3 Правила відповідності сесій роботам

- **Один робот = одна конкретна сесія**, а не один процес, проєкт чи тип агента. Три Claude Code в одному репозиторії = три роботи.
- Стабільний ключ робота — нормалізований `sessionId` з namespace джерела; не використовувати PID як єдиний ідентифікатор.
- Після появи нової сесії створюється робоче місце й робот; при перепідключенні браузера ті самі сесії не дублюються.
- Роботи одного проєкту за можливості сидять поруч у проєктній зоні. Додавання/видалення сесій не повинно хаотично переставляти всіх роботів.
- При збільшенні кількості сесій — розширення офісу або додаткові зони; для великої кількості роботів — спрощення сцени, підписів і анімацій. Точні пороги визначити після тестування.
- Після завершення сесії робот коротко показує завершення, після чого зникає з активного офісу або лишається як завершений на обмежений час (поведінка конфігурована). Історичні дані не видаляти автоматично разом із роботом.

### 6.4 Поведінка роботів: стани та анімації

| Реальний стан | Візуальна поведінка | Сигнал |
|---|---|---|
| `working` | Сидить за комп'ютером, друкує; екран має ненав'язливу анімацію | Зелений індикатор |
| `waiting` | Припиняє друкувати, піднімає руку; над столом з'являється помітний значок | Жовтий індикатор та позначка «потрібна увага» **лише коли підтверджено очікування користувача** |
| `idle` | Спокійна idle-анімація; пізніше може перейти до кавомашини/дивана | Нейтральний індикатор |
| `ended` | Встає, монітор згасає, робот залишає місце або поступово зникає | Позначка завершення |

- Анімації є **метафорами стану**, а не буквальними діями агента; ніколи не видавати декоративний рух за подію з логів.
- Якщо немає достатньо даних для достовірного стану, інтерфейс повинен показувати «невідомо / дані застарілі», а не вигадувати `idle` чи `waiting`. Для цього може знадобитися окремий UI-стан `unknown`, не обов'язково новий базовий статус демона.
- Для інструментів (`Read`, `Edit`, `Bash` тощо) можна показувати невелику піктограму або текст над монітором; це відображення реальної події, не симуляція виконання.
- Анімації не повинні перезапускатися на кожному SSE-оновленні, лише при реальній зміні релевантного стану.
- Нотифікації та звуки — пізніше, з можливістю вимкнення; `waiting` має бути помітним і без звуку.

### 6.5 Взаємодія з 3D-сценою

- **Клік на робота або його стіл**: вибір конкретної сесії, підсвічування робота, плавне наближення/зсув камери та відкриття детальної панелі цієї сесії.
- Повторний клік на іншого робота: панель перемикається на нову сесію без перезавантаження сторінки.
- Наведення: короткий tooltip з назвою агента, проєктом, статусом і поточною задачею (за наявності).
- Клік поза вибраним роботом або кнопка закриття: закриття панелі; кнопка «Показати весь офіс» повертає камеру до загального вигляду.
- Колесо миші/трекпад: zoom; drag по порожньому простору: pan. Обертання обмежене або вимкнене, щоб зберегти ізометричну композицію. Потрібно уникати конфлікту drag із вибором робота.
- Подвійний клік/клавіша за потреби: сфокусувати камеру на вибраній сесії. `Esc` закриває панель; клавіатурний вибір через список сесій.
- Пошук за проєктом/агентом фокусує відповідного робота; фільтр приховує або приглушує нерелевантні робочі місця без знищення стану сесій.
- Усі переходи короткі, плавні, без різких стрибків. Підтримати `prefers-reduced-motion`.

### 6.6 Детальна панель агента — головна вимога

**При натисканні на будь-якого робота показати максимально повну, доступну й достовірну інформацію саме про цю сесію.** Панель оновлюється live, поки вона відкрита; зміна статусу не скидає вибір або прокрутку. Панель має закриватися й відкриватися без втрати даних.

**Шапка:**
- Назва/тип агента (`Claude Code`, `Codex`), індивідуальний ID сесії та статус з часом останнього оновлення.
- Назва проєкту, репозиторій, гілка Git (якщо доступна), робоча директорія (`cwd`).
- Час старту, тривалість, остання активність; позначення завершеної сесії.
- Візуальний індикатор актуальності даних; явне «немає даних» замість вигаданих значень.

**Блок «Поточна задача»:**
- Повний текст поточної задачі / останнього релевантного запиту користувача (якщо його реально можна отримати), з можливістю розгорнути та скопіювати.
- Якщо задачу не можна достовірно визначити — `Невідомо`, з поясненням джерела/обмеження.
- Поточна дія та інструмент (наприклад, `Read`, `Edit`, виконання команди), шлях файлу/ціль дії, час початку; показувати лише доступні поля.
- Останній результат/помилка інструмента, якщо доступні; великі результати обрізати з можливістю розгортання.
- Окремо відображати `waiting for permission`, якщо цей стан підтверджений джерелом; не прирівнювати кожне `waiting` до дозволу.

**Вкладка Activity / Timeline:**
- Хронологія подій цієї сесії: старт, промпти, виклики інструментів, результати, помилки, зміни станів, завершення.
- Для кожної події: timestamp, тип, короткий опис, розгорнуті деталі, джерело даних (hook / log / process), якщо корисно.
- Фільтри за типами подій, пошук, автопрокрутка з можливістю призупинити її при ручному перегляді.
- Нові події додаються live, без перезаписування всієї історії та без стрибка scroll.

**Вкладка Details / System:**
- `sessionId`, тип агента, PID і стан процесу (якщо відомі), cwd, назва проєкту, Git branch, час старту/завершення.
- CPU %, RAM, час останньої активності, стан підключення й джерела телеметрії.
- Якщо PID не вдається надійно зіставити із сесією — показати `не визначено`, не приписувати чужі CPU/RAM.

**Вкладка Subagents:**
- Список дочірніх агентів, їхні статуси та задачі **лише якщо зв'язок parent-child реально визначається**.
- Натискання на субагента переводить до його детальної панелі; за наявності окремої сесії — до його робота або логічного представлення.
- Якщо джерело не надає таких даних — порожній стан `Субагентів не виявлено / дані недоступні`, а не вигадані зв'язки.

**Вкладка Logs / Raw events (можна після MVP):**
- Перегляд доступних записів сесії або структурованих raw-подій із позначенням джерела та часу.
- Копіювання окремих записів; довгі логи — пагінація/віртуалізація, обмеження обсягу в пам'яті.
- Обережне відображення команд, шляхів і промптів: маскування секретів, без автоматичного виконання чи відкриття небезпечних URL.

**Поведінка панелі:**
- Панель read-only: жодних кнопок, які зупиняють, змінюють або запускають агента.
- Дані, що не підтримуються конкретним агентом, приховувати або показувати як недоступні; не створювати хибного враження повноти.
- Якщо сесія завершилась, панель лишається відкритою та показує фінальний стан; користувач може переглянути вже отриману історію.
- Усі поля мають підтримувати довгі шляхи, Unicode, перенос тексту, копіювання та читабельність на невеликих екранах.

### 6.7 Реальні дані та інтеграція з демоном

- Дашборд отримує нормалізований стан і події через `/api/state` + SSE; 3D-компоненти підписуються на селектори Zustand, щоб не перемальовувати всю сцену на кожну подію.
- Розширити `Agent` за необхідності полями `sessionId`, `startedAt`, `endedAt`, `gitBranch`, `parentSessionId`, `dataFreshness`, `sourceCapabilities`; поля опціональні, якщо джерела їх не гарантують.
- Зберігати окремо **телеметрію**, **UI-стан** (`selectedSessionId`, camera target, filters) і **анімаційний стан**; UI не повинен змінювати реальні статуси агента.
- Для детальної панелі потрібні API отримання подій конкретної сесії, наприклад `GET /api/sessions/:id/events?cursor=...` (це пропозиція, остаточний контракт визначити при розробці). SSE передає нові події та зміни стану, а не всю історію щоразу.
- Після реконекту SSE отримати актуальний snapshot і коректно синхронізувати вибрану сесію; дублікати подій відкидати за стабільними ID.
- Приватні промпти, шляхи та команди залишаються локальними. Уникати сторонніх аналітичних SDK, CDN-ресурсів, що відправляють вміст сесій, і відкритого CORS.

### 6.8 Продуктивність, доступність і резервний режим

- Ціль: плавна взаємодія на цільовому Mac; конкретний FPS/ліміт агентів встановити після вимірювань, не обіцяти 60 FPS без тестів.
- Використовувати інстансинг повторюваних об'єктів, прості low-poly моделі, обмеження світла/тіней, адаптивну якість та мінімум зайвих React-рендерів.
- Відкладено завантажувати важку 3D-сцену; при відсутності WebGL або низькій продуктивності — **доступний 2D-список сесій із тією самою детальною панеллю**.
- Врахувати клавіатурну навігацію, контраст, текстові статуси поряд із кольорами та знижену анімацію.
- Розрізняти `daemon disconnected`, `no active sessions`, `loading`, `stale telemetry`, `permission/access unavailable`.

### 6.9 Межі MVP та майбутні покращення

**MVP інтерфейсу:** одна ізометрична кімната, прості 3D-роботи й столи, по одному роботу на сесію, чотири базові анімації станів, live-індикатори, вибір кліком, tooltip, pan/zoom/reset, права панель із шапкою, поточною задачею, інструментом, системними полями та доступними live-подіями; базовий список сесій як fallback.

**Після MVP:** складніші анімації (кава, пересування, вихід із кімнати), декілька проєктних зон, додаткові кімнати, візуальні зв'язки субагентів, повний пошук і фільтри таймлайну, розширені raw-логи, історія SQLite, сповіщення, менюбар, теми освітлення та персоналізація офісу.

**Критерії приймання інтерфейсу:**
1. Запуск двох сесій одного агента створює двох різних роботів.
2. Клік на кожного відкриває **його**, а не спільну, інформацію.
3. Поточна задача, інструмент і статус змінюються без refresh; при відсутності даних відображається чесне `невідомо`.
4. `waiting` візуально помітний; завершення сесії не закриває панель примусово.
5. Вибір, scroll панелі та позиція камери не скидаються від звичайних SSE-оновлень.
6. Перепідключення не створює дублікати роботів чи подій.
7. 3D-офіс не блокує моніторинг: доступний резервний 2D-список.
8. Усі дії залишаються read-only, а дані не покидають локальну машину.

## 7. Етапи

1. **Дослідження агентом перед реалізацією:** виконати пункти розділу 8, перевірити доступні події, ідентифікатори сесій, можливість отримати задачу, інструменти, PID і субагентів; зафіксувати обмеження. Не припускати, що всі поля доступні.
2. **Демон:** сканування процесів, hooks Claude Code, `/api/state`, SSE, стабільні ID сесій, нормалізація подій.
3. **Базова 3D-сцена:** ізометричний офіс, роботи, столи, прості стани, прив'язка роботів до реальних сесій.
4. **Взаємодія:** клік/hover, камера, вибір сесії, детальна read-only панель, live-таймлайн доступних подій.
5. **Codex:** підключення логів та статусів; однакова UX-модель для обох типів агентів із чесним відображенням недоступних полів.
6. **Історія та метрики:** SQLite, перегляд минулих сесій, розширений таймлайн, raw-події та субагенти (якщо дані доступні).
7. **Полірування:** оптимізація сцени, адаптивність, додаткові анімації, проєктні зони, нотифікації «агент чекає на мене», менюбар.

## 8. Дослідження: що треба з'ясувати (для агента)

Статус усіх пунктів: **не розпочато**. Нічого з наведеного нижче не підтверджено, це гіпотези та питання.

### 8.1 Claude Code: події та hooks
- Які події hooks існують і які поля приходять у кожній.
- Як налаштовуються hooks у `~/.claude/settings.json` (схема, matcher).
- Чи бувають неблокуючі (async) hooks, які таймаути.
- Чи можна дізнатися PID процесу Claude з hook (гіпотеза: через `$PPID`).
- Як відрізнити стан «чекає на дозвіл» від «завершив відповідь».
- Результат: таблиця «подія → поле → що з нього беремо».

### 8.2 Claude Code: файли сесій
- Де лежать транскрипти, як кодується шлях проєкту в назві папки.
- Структура записів jsonl: промпти, відповіді, виклики інструментів, субагенти, службові записи.
- Коли рядки дописуються (по повідомленню чи потоково), чи можливі неповні рядки.
- Як з файлу витягнути «поточну задачу».
- Результат: правила парсингу з прикладами реальних рядків.

### 8.3 Codex
- Де зберігаються сесії та в якому форматі.
- Чи є в Codex hooks або механізм сповіщень про події.
- Як визначити поточну задачу, інструмент, стан.
- Потрібен зразок реальних файлів з моєї машини.
- Результат: те саме, що в 8.1 та 8.2, для Codex.

### 8.4 macOS: процеси та зіставлення із сесіями
- Як надійно знайти процеси агентів (різні способи встановлення: native, npm).
- Як отримати cwd чужого процесу на macOS без зайвих прав.
- Як зіставити процес із конкретною сесією, якщо кілька агентів запущено в одній папці.
- Як виявити сесію, що завершилась без події (Ctrl+C, crash).
- Результат: алгоритм зіставлення та список відомих обмежень.

### 8.5 Live-доставка
- Чи достатньо chokidar на macOS для швидкого виявлення нових файлів та дописувань у великі jsonl.
- Читання хвоста з позиції, буферизація неповних рядків.
- Поведінка SSE при перепідключенні, обмеження кількості з'єднань.
- Результат: рекомендація й прості заміри затримки.

### 8.6 Інші способи запуску
- Чи сесії з IDE-розширень, headless-режиму та SDK пишуть ті самі файли й викликають ті самі hooks.
- Результат: що охоплюємо в MVP, а що ні.

### 8.7 Безпека та приватність
- Дашборд показує промпти й команди: переконатися, що все залишається локальним (127.0.0.1, відсутність CORS-відкриття).
- Чи варто маскувати секрети у відображенні.

### 8.8 3D-інтерфейс та повнота інформації про сесію
- Які поля з розділу 6.6 реально доступні для Claude Code та Codex, які лише іноді, а які недоступні? Створити матрицю `поле × джерело × достовірність × затримка`.
- Чи можна стабільно відрізняти декілька одночасних сесій одного типу й проєкту та відстежувати їх після перезапуску демона?
- Які події потрібні для достовірного `waiting for permission` і для parent-child зв'язків субагентів?
- Які low-poly 3D-ресурси й анімації можна створити або використати локально без порушення ліцензій? Чи достатньо React Three Fiber/Drei для потрібної продуктивності?
- Який оптимальний спосіб синхронізації snapshot + SSE-дельт із 3D-сценою та панеллю, без зайвих рендерів?
- Результат: матриця доступності полів, прототип сцени з декількома роботами та заміри FPS/затримки на цільовому Mac.

## 9. Відкриті питання

- Чи потрібне в майбутньому підключення власних multi-agent систем (універсальний `POST /events`).
- Як вебу підключатися до демона: браузер напряму до SSE демона (потрібен CORS лише для локального origin) чи через проксі в route handler Next.js.
- Яку глибину історії зберігати.
- Чи потрібні дії над агентами (зупинка, відкриття терміналу) після MVP. Поточне рішення: read-only.
- Як довго показувати завершених роботів в офісі до прибирання зі сцени.
- Які саме деталі промптів/команд відображати за замовчуванням, а які приховувати за кліком для приватності.
- Чи потрібні кастомізація роботів, планування офісу й кілька кімнат після MVP.
