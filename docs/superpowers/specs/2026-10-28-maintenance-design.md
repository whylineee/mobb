# Усунення проблем AgentWatch

Статус: погоджено користувачем («давай»). Дата: 2026-10-28.

## Мета і межі

Виправити п'ять груп проблем із проведеного аналізу: документацію, необмежене зберігання, зайве завантаження деталей, великі UI-компоненти та відсутність автоматизованих перевірок із контрольованими версіями залежностей.

Зберегти поточний вигляд, поведінку камери, доступність, протоколи автентифікації й підтвердження живих сесій. Не встановлювати hooks у реальні налаштування користувача під час розробки. Не додавати новий сервер або фреймворк.

## Підхід

Пропоную локальні зміни в наявних чотирьох пакетах: SQLite лишається джерелом даних, пам'ять демона стає обмеженим кешем, а оновлення текстових деталей отримують окрему версію. UI ділиться за відповідальністю зі збереженням поточного DOM і 3D-композиції.

Повне перенесення стану в нове сховище збільшило б обсяг міграції без потреби. Просте обмеження кількості сесій у Map із видаленням решти втратило б поточний стан відкритих агентів. Обраний мною для цієї пропозиції варіант — обмежений кеш із читанням повного стану з SQLite.

## Зберігання — запропоновані значення

- Історія подій: не більше 7 днів для всіх сесій, включно з відкритими.
- Додаткові межі історії: 10 000 останніх подій на сесію та 100 000 подій загалом. При досягненні межі видаляються найстаріші події; час події та seq забезпечують детермінований порядок.
- Поточний знімок відкритої сесії зберігається незалежно від віку її історії. Це дозволяє лишити задачу, статус і активні виклики після обрізання таймлайна.
- Уточнення після регресійного огляду: захист раніше підтвердженого відкритого знімка зберігається окремо від lifecycle після перезапуску. Відкритість стає unknown, але знімок не видаляється лише через старий lastActivityAt; підтверджене завершення знімає захист.
- Завершені сесії та непідтверджені сесії без захищеного раніше відкритого знімка видаляються після 7 днів без активності.
- Кеш повних сесій у пам'яті: максимум 256 записів із витісненням давно не використаних. Витіснення з кешу не видаляє рядок SQLite і не означає завершення сесії.
- Snapshot запитує максимум 200 пріоритетних сесій із SQLite; omittedSessions рахується за БД, не за кешем.
- На старті не завантажувати всю таблицю в масив. Повторне підтвердження живого стану після перезапуску має лишитися коректним також для сесій поза кешем.
- Обмеження історії застосовуються до наявної БД під час стартового очищення та підтримуються під час роботи. Поточні знімки й історія мігруються сумісно з наявною схемою, без скидання БД.
- Обрізана історія не має воскресати через повторне читання старого транскрипту або знімати чинні обмеження. Зберегти коректність дедуплікації та злиття hook/log.
- У README явно пояснити, що за високої активності доступна історія може бути коротшою за 7 днів. Це зміна політики видалення локальної історії, яка потребує погодження.

Конкретні числові межі — моя пропозиція, користувач їх ще не погодив. Це обмеження кількості записів, не обіцянка точного ліміту RAM або розміру файлу SQLite: розмір поточного стану відкритих сесій залежить від їх кількості й вмісту.

## Завантаження деталей

- Додати до контракту Session необов'язкове поле detailsRevision.
- Версію деталей змінюють події, які можуть змінити текст або семантичний стан сесії. Звичайний updateProcess не змінює її.
- Повна відповідь і SSE summary несуть одну версію деталей для одного стану.
- Панель отримує повні деталі при виборі сесії, зміні detailsRevision або відновленні з'єднання. Оновлення CPU/RAM не запускає повторне завантаження тексту.
- Для старих даних без detailsRevision зберегти сумісний fallback.
- mergeDetails перевіряє версію деталей, зберігає свіжі метрики із summary і відхиляє застарілі HTTP-відповіді, навіть якщо часові мітки однакові.

## Межі UI-модулів

- Office: окремі модулі для інстансів/меблів і кімнати, камери та обробника помилок; Office лишається композицією сцени.
- SessionPanel: окремі вкладки огляду, активності й технічних деталей; спільні елементи тексту й копіювання; hook завантаження даних.
- Dashboard: окремі Login і SessionList, а також hook життєвого циклу підключення/viewport за потреби. Стан навігації лишається зрозумілим і локальним.
- Не ділити файли лише заради кількості рядків. Конкретні назви й інтерфейси нових модулів залишаю виконавцю.

## Документація та інструменти

- README: негайне зникнення робота після Stop/SessionEnd; idle-сесія зберігається у списку; коректний опис текстового ліміту та збереження Retina DPR зі зниженням деталізації/тіней.
- Текстовий ліміт: зберегти нинішню реалізацію й чесно описати 65 536 одиниць UTF-16, прибравши твердження про 64 KiB.
- docs/verification.md лишається історичним звітом із явною приміткою про дату/commit і посиланням на новий звіт після змін.
- Замінити latest у package.json точними версіями з поточного pnpm-lock.yaml. Зберегти workspace:*; не оновлювати фактичні версії пакетів. Перевірити frozen-lockfile після синхронізації specifier.
- Додати GitHub Actions для push і pull_request: Node 24, pnpm 11.25.0, frozen install, unit/integration, typecheck, format:check, production build і Chromium E2E. Використати macOS runner, оскільки це цільова платформа продукту.
- Обмежити CI permissions до contents:read; зберігати діагностику браузерних помилок як artifacts без реальних приватних даних.
- Додати Dependabot для контрольованих щотижневих пропозицій оновлення npm-пакетів та GitHub Actions. Автоматичного злиття немає.
- Вибір конкретних актуальних major-версій CI actions перевірити за офіційною документацією перед реалізацією.

## Перевірки

Перш ніж змінювати поведінку, додати тести й побачити очікувані помилки для:

1. Обрізання історії відкритої сесії зі збереженням її поточного стану; межі на сесію/загалом; коректне продовження пагінації після очищення.
2. Читання сесії після витіснення з кешу, правильного omittedSessions і відновлення сесії поза кешем після перезапуску.
3. Старого HTTP-відгуку з тим самим часом, process-only оновлення без нового запиту деталей та нового тексту, який усе ж завантажується.
4. Повторного читання транскрипту після обрізання історії без її безмежного відновлення.

UI-виділення перевірити наявними сценаріями вибору агента, камери, фокусу клавіатури, мобільних панелей, timeline, WebGL fallback і бюджету рендерингу. Для простого перенесення компонентів не додавати тести, які лише дублюють структуру файлів.

Фінальні команди: pnpm install --frozen-lockfile, pnpm test, pnpm typecheck, pnpm format:check, pnpm build, pnpm test:e2e. Окремо перевірити синтаксис workflow; фактичний запуск GitHub-hosted CI можливий лише після відправлення змін на GitHub і не заявляється як локально виконаний.

## Порядок

1. Зберігання й кеш із міграцією та регресійними тестами.
2. Версія деталей і виділення завантаження панелі, тести HTTP/UI.
3. Виділення решти UI-модулів.
4. Версії залежностей, CI, документація й повний прогін перевірок.
